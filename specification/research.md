## Problem Statement

O usuário quer um aplicativo web para gerenciar a própria coleção de bookmarks,
no estilo do [booky.io](https://booky.io). Qualquer pessoa pode **ver** os
bookmarks, mas **apenas o administrador** pode criar, editar ou remover. O app
é hospedado no **GitHub Pages** (hospedagem estática, sem backend próprio) e o
**banco de dados é o Firebase** (Firestore + Auth). É necessário
importar/exportar arquivos compatíveis com o booky.io.

A interface e a arquitetura devem **replicar o projeto Estante**
(https://github.com/willycornelissen/estante) — um app de biblioteca pessoal que
o usuário já mantém com exatamente essa stack: React + Vite, GitHub Pages,
Firebase (Firestore + Auth), leitura pública + escrita só do admin.

## Decisões (confirmadas com o usuário)

| Decisão | Escolha |
|---|---|
| Banco de dados | **Firebase** — Firestore (NoSQL, plano Spark) + Firebase Auth |
| Modelo de acesso | **Leitura pública; escrita exclusiva do admin** (Security Rules) |
| Interface/arquitetura | **Replicar o Estante** (repo de referência do usuário) |
| Stack | **React + Vite** (como o Estante), deploy via GitHub Actions → Pages |
| Fidelidade ao booky.io | **Espelho de features principais** (categorias coloridas, busca, notas, favicons, tema claro/escuro, import/export HTML) |
| Intercâmbio de arquivos | **Formato Netscape HTML** (import/export compatível com booky.io e navegadores) |
| Estrutura de dados | **Coleções → Categorias → Bookmarks**, many-to-many via **tabela de associação** (`bookmark_categories`). Um bookmark pode estar em várias categorias e coleções |
| Frontend | **Sidebar vertical fixa de coleções** (estilo Notion/Linear), header sticky com busca global, conteúdo com categorias em cards coloridos. Menu horizontal do booky.io descartado pelo usuário |

## Key Insights

### 1. O Estante é o blueprint completo — não reinventar

Analisei o repositório `willycornelissen/estante`. É um app da mesma família
e resolve quase todas as decisões de arquitetura por analogia:

- **`firestore.rules`**: leitura pública, escrita só do admin por e-mail:
  ```
  match /books/{bookId} {
    allow read: if true;
    allow write: if request.auth != null
      && request.auth.token.email == 'willy.cornelissen@gmail.com';
  }
  ```
  Para o marcador: mesma regra sobre a coleção de bookmarks. **A segurança fica
  nas regras do Firestore, nunca no frontend.**
- **`src/lib/auth.js`** + **`src/lib/firebase.js`**: wrappers finos de
  `onAuthStateChanged`, `signInWithEmailAndPassword`, `signOut`, `initializeApp`
  com config vinda de `import.meta.env.VITE_*`. Firebase é **inicializado só se
  houver config** (graceful fallback quando `.env` não está preenchido).
- **Gating do admin no frontend** (`src/App.jsx`): `isAdmin = user.email ===
  VITE_ADMIN_EMAIL`. Mostra/esconde controles de edição; mas a segurança real
  está nas regras.
- **`src/lib/books.js`**: `subscribeBooks` usa `onSnapshot(query(...))` com
  listener em tempo real; CRUD via `addDoc/updateDoc/deleteDoc` +
  `serverTimestamp()`. Nenhum backend próprio.
- **`vite.config.js`**: `base: hasCname ? '/' : (process.env.VITE_BASE || '/estante/')`
  — lida com o caminho do repo no GitHub Pages.
- **`.github/workflows/deploy.yml`**: build com `npm ci && npm run build`,
  variáveis `VITE_*` injetadas via `secrets`, deploy com `actions/deploy-pages`.
- **Login**: formulário inline (sem tela de rota), `signUp` removido — só o
  admin entra (a conta é criada manualmente no console Firebase).

### 2. O formato do booky.io é o formato Netscape HTML

Investiguei o código-fonte aberto (`github.com/nthiebes/booky.io`, só o
frontend React/Redux):

- **Import**: `POST /bookmarks/import` recebe o **HTML bruto** do arquivo de
  bookmarks do navegador (padrão Netscape que Chrome/Firefox exportam), com
  checkbox `importAsCollections` (pastas viram coleções).
- **Export**: `GET /bookmarks/export` baixa um **arquivo HTML** no mesmo padrão
  (opção `?noIcons=1` para omitir favicons).
- **Sem API pública**: booky.io não oferece REST API. O único canal é o arquivo
  HTML Netscape.

**Conclusão**: "importar/exportar arquivos com o booky.io" = **compatibilidade
com Netscape HTML**. Qualquer app que leia/escreva esse formato é intercambiável
com o booky.io e com os navegadores. Isso não muda com o Firebase — é só um
parser/writer no cliente.

### 3. Modelo de dados do booky.io (referência para o schema Firestore)

Hierarquia observada no source: `Dashboard → Category → Bookmark`.

- **Category**: `{ id, name, color, position }`
- **Bookmark**: `{ id, name, url, note, favicon, position }`
- **Sem tags, sem pastas aninhadas** — plano: categoria tem uma lista de
  bookmarks. Favicon é resolvido server-side no booky.io; num app estático
  usamos um serviço público (Google `s2`, DuckDuckGo `icons.duckduckgo.com`),
  ou armazenamos a URL do favicon no documento (o Estante guarda a capa).

**Estrutura (definida pelo usuário)**: bookmarks são agrupados em **coleções**,
cada coleção com **várias categorias**. Um bookmark pode estar armazenado em
**coleções e categorias diferentes** — ou seja, relação **many-to-many** entre
bookmark e categoria (e, por herança, entre bookmark e coleção). A modelagem
escolhida usa **tabela de associação**.

**Schema Firestore sugerido** (espelhando o Estante + booky.io, com associação):

- Coleção `collections`: `{ id, name, position, color?, uid, createdAt, updatedAt }`
- Coleção `categories`: `{ id, collectionId, name, position, color, uid, createdAt, updatedAt }`
- Coleção `bookmarks`: `{ id, name, url, note, favicon, uid, createdAt, updatedAt }`
- Coleção `bookmark_categories` (associação many-to-many): `{ id, bookmarkId, categoryId }`

A associação é a fonte de verdade de "onde está cada bookmark": um bookmark
pertence a uma coleção indiretamente, por estar em uma categoria daquela
coleção. Isso permite o mesmo bookmark aparecer em várias coleções e categorias
sem duplicar dados. As quatro coleções são simples de proteger com as regras e
de percorrer em memória (o app já carrega tudo via `onSnapshot`).

### 4. Gotcha: localStorage não é mais necessário — e o gotcha de origin some

Com o Firestore como fonte de verdade, **não precisamos de localStorage** (o
que elimina o problema do localStorage compartilhado entre repos do mesmo
usuário no GitHub Pages). Os bookmarks vivem no banco, acessíveis de qualquer
dispositivo/navegador após login do admin para escrita e publicamente para
leitura. Cache em memória via estado React + `onSnapshot` é suficiente.

### 5. Busca no Firestore = filtro em memória

O Firestore não tem full-text nativo. Para uma coleção pessoal (centenas de
bookmarks, ~KBs de dados), a abordagem correta (como o Estante) é **carregar a
coleção inteira via `onSnapshot` e filtrar em memória** no cliente. Busca
instantânea por título/URL/nota/tag, sem custo de leitura por tecla. Para este
volume, Algolia/Typesense seriam over-engineering.

### 6. "Admin-only" resolvido de verdade

Ao contrário da hipótese inicial (localStorage = acesso por obscuridade), o
Firebase dá **autenticação real**:
- `allow read: if true` — visitantes veem o catálogo.
- `allow write: if request.auth != null && request.auth.token.email == '<admin>'`
  — só o e-mail do admin grava.
- Conta do admin criada manualmente no console Firebase; `signUp` removido do
  frontend (padrão do Estante). Falha honesta: se o e-mail das regras ≠ e-mail
  da conta, a escrita falha no Firestore (regras são a barreira).

### 7. Interface "estilo Estante" para bookmarks

O Estante é dark, single-user, tipo galeria: busca no topo, filtros em pills,
cards com capa/ícone, modal de detalhe, CRUD em modais/formulário. Para
bookmarks, a tradução é direta: **colunas de categorias coloridas com cards de
bookmarks** (favicon + título + URL + nota), busca global no topo, pills de
filtro por categoria, modal criar/editar, tema claro/escuro. A UI.md do Estante
serve de referência visual.

## Frontend — Decisão de Layout (confirmada com o usuário)

O usuário rejeitou o **menu horizontal de coleções** do booky.io (escala mal:
linha infinita com muitas coleções, esconde a hierarquia coleção → categoria →
bookmark, compete com a busca no topo). Direção escolhida:

**Sidebar vertical fixa de coleções (estilo Notion/Linear)**

- **Sidebar** (`--sidebar-width: 240px`, fundo `bg-stone-900`): lista vertical
  de coleções com contador de bookmarks; categorias da coleção ativa como
  sub-itens indentados — hierarquia de 3 níveis visível sem rolagem horizontal.
- **Header sticky** (translúcido `backdrop-blur`, padrão do Estante): logo serif
  "Marcador." (acento âmbar), busca global no centro (filtro em memória), ações
  à direita — "Adicionar bookmark" (admin) e login/sair.
- **Conteúdo**: categorias da coleção ativa em grid de cards coloridos;
  bookmarks dentro como cards com favicon + título + URL + nota.
- **Mobile**: sidebar vira **drawer** (hambúrguer + overlay), porque 240px fixos
  não cabem em 375px.
- **Acessibilidade** (checklist da skill): botões ≥44px, focus visível,
  `prefers-reduced-motion`, contraste 4.5:1, SVG icons (Lucide/Heroicons), sem
  emoji como ícone.
- **Paleta**: mantém a identidade do Estante (dark stone + âmbar), validada pela
  skill como adequada para tool pessoal (Dark OLED + Flat Design, WCAG AA).

Alternativas avaliadas e descartadas:
- **Home em grid de coleções + sidebar ao entrar** — combinava dois padrões, mas
  o usuário preferiu consistência com sidebar fixa.
- **Dropdown de coleção + breadcrumb** — chrome mínimo, mas esconde a hierarquia.
- **Menu horizontal (booky.io)** — rejeitado pelo usuário.

## Approaches Considered

### Approach A: Espelho do Estante + Firestore (ESCOLHIDO)
  Summary: React + Vite, quatro coleções Firestore (`collections`, `categories`,
  `bookmarks`, `bookmark_categories`), Auth email/senha, regras
  leitura-pública/escrita-admin, parser/writer Netscape HTML no cliente, deploy
  GitHub Actions → Pages. Interface dark estilo Estante adaptada para bookmarks,
  com hierarquia coleções → categorias e many-to-many via associação.
  Effort: M (3-5 dias)
  Risk: Baixo — o usuário já opera a mesma arquitetura no Estante em produção
  Pros: Stack comprovada pelo próprio usuário; dados no banco (não perdíveis,
        multi-dispositivo); admin-only real via Auth + regras; import/export
        booky.io via Netscape HTML
  Cons: Config inicial do Firebase (console, regras, conta admin, secrets do
        Actions); favicons precisam de serviço público
  Reuses: Padrões completos do `estante` (auth.js, firebase.js, deploy.yml,
          firestore.rules, vite.config.js)

### Approach B: localStorage + export (explorada antes, superada)
  Summary: SPA vanilla, dados só no navegador, sem banco.
  Effort: S (1-2 dias)
  Risk: Baixo, mas **não atende ao requisito do usuário** — ele definiu o
  Firebase como banco e quer o padrão do Estante (leitura pública em qualquer
  dispositivo)
  Pros: Zero infra
  Cons: Preso a 1 dispositivo; perde dados; "admin-only" não é segurança real;
        contradiz a decisão do usuário
  Reuses: — (descartada)

### Approach C: JSON commitado no repo como "banco"
  Summary: Bookmarks como arquivo no repositório, escrita via GitHub API/commit.
  Effort: M
  Risk: Alto — cada edição exige push/autenticação, conflitos, redeploy; Git não
  é banco para dados que mudam a cada clique
  Pros: Backup natural no Git
  Cons: Frágil e lento; inferior ao Firestore em tudo para este caso
  Reuses: — (descartada)

## RECOMMENDATION

**Approach A (espelho do Estante + Firebase/Firestore)**, porque atende
exatamente o que o usuário pediu: Firebase como banco, leitura pública +
escrita só do admin, GitHub Pages, e import/export compatível com booky.io
(Netscape HTML). É a arquitetura que o usuário já opera em produção no Estante,
o que reduz o risco a quase zero e permite reutilizar os padrões de código
(auth, firebase, deploy, regras) quase verbatim.

## Concerns

- **Config Firebase é o gargalo de onboarding** — sem ela, o app deve degradar
  com graça (mensagem "Firebase não configurado", como o Estante faz).
- **Favicons**: serviços públicos podem rate-limit/bloquear; ter fallback de
  letra inicial (o próprio booky.io tem fallback `default`).
- **XSS no import**: o parser HTML Netscape deve usar DOMParser/textContent,
  nunca `innerHTML` com conteúdo externo.
- **Regras desatualizadas**: se o e-mail do admin mudar, atualizar
  `firestore.rules` + re-deploy do Firestore, senão escrita falha.
- **Associação many-to-many**: ao remover um bookmark ou categoria, limpar os
  documentos da `bookmark_categories` (órfãos); consistência garantida no
  cliente, já que as regras protegem por e-mail, não por integridade relacional.
